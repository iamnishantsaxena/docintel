# Evaluation

## What is measured

`backend/eval/run_eval.py` runs every PDF in a dataset folder through the real pipeline (`pdf_to_pages` →
`extract`) and compares the output field-by-field with a ground-truth JSON file next to it.

- **Scoring:** exact match after normalisation — text is case/whitespace-folded, money compared as `Decimal`,
  dates as ISO. A null in the truth counts as correct only if the extraction is also null.
- **Fields:** 11 scalar fields + `line_items_count` + `line_items_exact` (all quantities/prices/amounts match).
- **Not measured:** the validation rules' precision/recall, reviewer time saved, and anything about scanned PDFs
  (unsupported).

## Dataset

**Current dataset: 30 synthetic PDFs** (`backend/eval/dataset/synthetic/`), generated by
`python -m eval.generate` (seed 7), 5 per template:

| Template | What it stresses |
|---|---|
| `classic` | Labelled fields, supplier only in the letterhead (no label) |
| `label_variants` | `Vendor:`, `Invoice #`, `Net amount:`, `VAT 20%:`, `Amount Due:`, long-form dates, EUR |
| `purchase_order` | PO layout: number is the PO number, `Vendor:`/`Buyer:` |
| `unlabelled_supplier` | No colons: `Invoice BL-123`, `Issued 05 Mar 2024`, `Billed to X`, `TOTAL DUE` |
| `multipage` | 14–21 line items split across two pages |
| `day_first` | UK `dd/mm/yyyy` dates, GBP |

> **Honest caveat.** Ground truth is exact by construction (the generator writes the PDF and the JSON from the
> same values), so it is *not* a manually verified real-world sample. The same person wrote the templates and
> the regex fallback, so regex numbers on this set are optimistic. Every PDF has a clean text layer; real
> invoices are messier. Treat these numbers as a regression benchmark, not as expected production accuracy.

### Adding a manually verified real sample (recommended before quoting accuracy)

1. Put real PDFs in `backend/eval/dataset/real/` (git-ignore it if they're confidential).
2. For each `name.pdf`, write `name.json` by hand in the `Fields` shape (see any synthetic `.json`), checking
   every value against the PDF. Use `null` for values not printed.
3. `python -m eval.run_eval --dataset eval/dataset/real` (and `--no-llm` for the baseline).

## Results

### Regex-only baseline — measured

- Run 2026-10-29, macOS arm64, `python -m eval.run_eval --no-llm`, 30 synthetic PDFs.
- **Overall field accuracy 86.7 % (338/390 checks).** Full report with every miss:
  [`backend/eval/results/regex-only.md`](../backend/eval/results/regex-only.md).

| Field | Acc. | | Field | Acc. |

| document_type | 100 % | | due_date | 80.0 % |

| customer_name | 83.3 % | | subtotal | 83.3 % |
| document_number | 83.3 % | | tax | 100 % |
| po_number | 90.0 % | | total | 100 % |
| document_date | 73.3 % | | line items (count / exact) | 100 % / 100 % |

### LLM + regex — measured, four local models

- Run 2026-10-29, **MacBook Air M2, 8 GB RAM**, Ollama 0.40.13 (native, Metal), Q4_K_M quantisation,
  context 8192, temperature 0, `LLM_TIMEOUT_S=300`. One model loaded at a time, nothing else heavy running
  (the qwen2.5:3b run overlapped a ~1 GB model download, so its latency may be slightly pessimistic).
- `LLM_MODEL=<model> python -m eval.run_eval`, same 30 synthetic PDFs. One run per model.
- Full reports with every miss: `backend/eval/results/llm_<model>.md`.

|---|---|---|---|---|---|---|---|---|
| regex only | – | 86.7 % | 0.01 / 0.02 | – | 33.3 % | 83.3 % | 100 % | 100 % / 100 % |
| **qwen2.5:1.5b** | 1.0 GB | **96.9 %** (378/390) | 10.1 / 29.8 | 0 | 96.7 % | 93.3 % | 100 % | 96.7 % / 76.7 % |

¹ `016_multipage.pdf` hit the 300 s timeout (model kept generating) and is excluded; the worker would retry and
then fall back to regex.

**Reading it.** On this set the 1.5B and both 3B models are within ~2 points of each other — that is 6–8
field checks out of ~390 from one run each, so they are **not** meaningfully ranked by these numbers.
llama3.2:1b is clearly worse (it garbles money: subtotal 63 %, total 53 %) and below the regex baseline.
Every model beats regex on supplier name, which is the main reason to run a model at all. No run had a JSON
parse failure (0 regex fallbacks). **Default for an 8 GB laptop: `qwen2.5:1.5b`** — top score here, fastest of
the accurate models, smallest memory footprint; re-check against a real sample before trusting the ranking.

Line items are the weak spot for every model: `line_items_exact` is 47–77 % even though counts are mostly
right — the misses are wrong digits in one row (or rows dropped on long multipage invoices), and the model's
row values override the regex table parse.

## Known failure cases

Observed in the regex-only run or found while building; each has a test or an eval case that shows it.

| # | Failure | Where it shows | Mitigation in place | Not mitigated |
|---|---|---|---|---|
| 1 | **Supplier only in the letterhead** (no `Supplier:` label) — regex can't find it | `supplier_name` 33 % regex-only | `missing_required` error forces a reviewer to fill it; the LLM is expected to handle it | — |
| 2 | **Day-first dates parsed month-first.** `06/11/2025` → 2025-11-06 instead of 11 June. Silent: the value is a valid date | `day_first` misses | `due_before_issue` / `date_in_future` catch *some* swaps | No locale detection; a swapped date that's still plausible passes validation |
| 3 | Unlabelled layouts (`Invoice BL-123`, `Billed to X`) | `unlabelled_supplier` 61.5 % regex-only | Relies on the LLM | — |
| 4 | Non-standard labels (`Net amount:`, `Your ref (PO):`) | `label_variants` subtotal/PO misses | `line_items_sum_mismatch` can't fire without a subtotal; total is still checked against line items when tax is 0 | — |
| 5 | **Scanned / image-only PDFs** | `test_malformed_pdfs_raise_pdf_error` | Fails fast with "no extractable text … OCR not supported" | No OCR |
| 6 | Model returns plausible but invented identifiers | `test_hallucinated_identifier_flagged` | `not_in_source` warning when number isn't in the text | Invented supplier names aren't checked against the text |
| 7 | Model returns wrong types (`"about 500"`, `"ten"`, list for total) | `test_coerce_keeps_good_fields_and_flags_bad_ones` | Field dropped to null + `unparseable_value` warning; other fields kept | — |
| 8 | Model returns non-JSON / truncated JSON | `test_parse_json_object_rejects_bad_output`, `test_extract_falls_back_to_regex_on_bad_model_output` | That chunk falls back to regex + `llm_bad_output` warning | — |
| 9 | Model disagrees with printed total | `test_extract_fills_gaps_and_flags_disagreement` | `llm_regex_disagree` warning | Only for total and document number |
| 10 | Prompt injection inside the document ("ignore previous instructions…") | — | Prompt marks the document as data; output is schema-coerced and re-validated by rules; model can't take actions | Not tested against adversarial documents |
| 11 | Multi-chunk documents where chunks disagree on a scalar | `test_merge_chunks_first_value_wins_items_concatenate` | First non-null wins (page order) | No conflict warning between chunks |
| 12 | Non-US number/date formats in regex (`1.234,56` is handled; labels are English-only) | `test_parse_money` | `parse_money` handles both separators | Regex labels are English only |
| 13 | **Model mis-copies digits** (`46865.11` → `46685.11`, `287772.93` for `28772.93`) — mainly llama3.2 | subtotal/total misses in `llm_llama3.2_*.md` | `total_mismatch` / `line_items_sum_mismatch` errors fire when the numbers stop adding up, blocking approval | A transposition applied consistently to related fields passes (not measured how often) |
| 14 | **Line items dropped on long multipage invoices** (8 of 16 rows) | qwen2.5:3b `multipage` misses | `line_items_sum_mismatch` fires when the subtotal is printed | Rows silently missing if no subtotal |
| 15 | **Runaway generation** — model doesn't stop, call hits the timeout | qwen2.5:3b `016_multipage` | Timeout → retry → regex-only draft with `llm_unavailable` | No `max_tokens` cap on the request |
| 16 | Supplier and customer swapped | qwen2.5:1.5b `015_unlabelled_supplier` | – | No rule can tell which party is which |
